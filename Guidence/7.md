# FreeRTOS ISR 到任务事件路径改造记录

本文承接 `6.md`，记录本次提交中将 UART2 外部中断从“ISR 内直接打印验证”推进到“ISR 投递 Queue、任务上下文消费”的改造过程。


提交时间：

```text

```

本次提交涉及：

```text
trusted_domain/build/trusted_fw.hex
trusted_domain/driver/debug_log.c
trusted_domain/driver/irq.c
trusted_domain/main.c
```

当前目标是把上一阶段已经打通的中断链路：

```text
uart2 RX interrupt
  -> PLIC pending
  -> hart7 S-mode external interrupt
  -> FreeRTOS trap entry
  -> handle_interrupt()
  -> plic_claim()
  -> drain UART RX FIFO
  -> plic_complete()
```

继续推进为更接近真实系统的事件路径：

```text
uart2 RX interrupt
  -> handle_interrupt()
  -> ns16550_getc_nonblock()
  -> xQueueSendFromISR()
  -> portYIELD_FROM_ISR()
  -> vUartRxTask
  -> xQueueReceive()
  -> debug_log()
```

## 当前结论

本次改造完成后，UART2 RX 中断处理不再在 ISR 中直接打印字符，而是在 ISR 中尽快读取 RX FIFO，并把字符投递到 FreeRTOS Queue。真正的字符打印放到 `vUartRxTask` 中执行。

这样做的意义是：

- ISR 中保留必要的硬件处理：claim IRQ、读空 RX FIFO、complete IRQ。
- 字符处理逻辑进入任务上下文，避免在中断上下文里做 polling UART 输出。
- 使用 `xQueueSendFromISR()` 和 `xQueueReceive()` 验证 FreeRTOS ISR-safe API 与任务唤醒路径。
- 使用 `portYIELD_FROM_ISR()` 让被唤醒的高优先级消费任务尽快运行。

当前工作区在写本文前是干净的，最近一次提交已经包含代码和 `trusted_fw.hex` 的改动。本文作为后续文档记录新增。

## 改动一：debug_log 支持 `%c`

文件：

```text
trusted_domain/driver/debug_log.c
```

原来的 `debug_log()` 只支持：

```text
%x
%p
%d
%s
%%
```

本次为了打印收到的 UART 字符，新增了 `%c`：

```c
case 'c':
    ns16550_putc((char)va_arg(ap, int));
    break;
```

这里 `va_arg(ap, int)` 是必要的。因为在 C 的可变参数调用里，`char` 会经过 integer promotion，以 `int` 的形式传入。

需要注意：当前 `debug_log()` 仍然不是完整 `printf`，不支持宽度、补零等格式。因此下面这种格式不能使用：

```c
debug_log("rx: 0x%02x '%c'\n", ...);
```

`%02x` 会被当前 formatter 当成未知格式，输出 `?`。所以当前 RX 日志使用更简单的：

```c
debug_log("rx: %x '%c'\n", (unsigned long)(unsigned char)ch, ch);
```

## 改动二：irq.c 中引入 UART RX Queue

文件：

```text
trusted_domain/driver/irq.c
```

本次在中断分发文件中加入 FreeRTOS Queue 支持：

```c
#include <FreeRTOS.h>
#include <queue.h>
```

并定义全局队列句柄：

```c
QueueHandle_t xUartRxQueue = NULL;
```

该队列由 `main.c` 在启动调度器前创建，由 ISR 负责投递字符，由 `vUartRxTask` 负责消费字符。

UART2 IRQ 的处理逻辑从上一阶段的：

```text
打印 plic: uart2 irq
读空 RX FIFO
complete IRQ
```

改成：

```text
claim UART2_IRQ
循环读取 RX FIFO
如果 xUartRxQueue 已创建，则 xQueueSendFromISR()
complete UART2_IRQ
portYIELD_FROM_ISR()
```

关键代码路径：

```c
BaseType_t xHigherPriorityTaskWoken = pdFALSE;

if (irq == UART2_IRQ) {
    int ch;
    while ((ch = ns16550_getc_nonblock()) >= 0) {
        if (xUartRxQueue != NULL) {
            char c = (char)ch;
            xQueueSendFromISR(
                xUartRxQueue, &c,
                &xHigherPriorityTaskWoken);
        }
    }
}

plic_complete_hart7(irq);
portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
```

这里仍然保留“先读空 RX FIFO，再 complete PLIC”的顺序。原因是 UART 设备侧 RX 条件如果还存在，PLIC complete 后会马上再次 pending，容易形成中断风暴。

## 改动三：main.c 创建 Queue 和消费任务

文件：

```text
trusted_domain/main.c
```

本次在 `main.c` 中引入 Queue API：

```c
#include <queue.h>
```

并声明 `irq.c` 中定义的队列句柄：

```c
extern QueueHandle_t xUartRxQueue;
```

在打开 UART2 RX 中断前创建队列：

```c
xUartRxQueue = xQueueCreate(64, sizeof(char));
ns16550_enable_rx_irq();
```

这个顺序很重要。`ns16550_enable_rx_irq()` 一旦打开设备侧 RX interrupt，如果 UART RX FIFO 中已经有数据，后续调度器开启 S-mode external interrupt 后就可能进入 ISR。队列必须在这之前准备好，否则 ISR 只能 drain 字符，无法投递给任务。

新增消费任务：

```c
static void vUartRxTask(void *p_arg)
{
    char ch;

    for(;;)
    {
        if (xQueueReceive(xUartRxQueue, &ch,
                          portMAX_DELAY) == pdTRUE)
        {
            debug_log("rx: %x '%c'\n",
                      (unsigned long)(unsigned char)ch, ch);
        }
    }
}
```

并在 `vTaskCreate()` 中创建：

```c
xTaskCreate(vUartRxTask, "vUartRxTask", 2048, NULL, 5, NULL);
```

`vUartRxTask` 使用优先级 5，高于 `task1` / `task2` 的优先级 4。这样当 ISR 中 `xQueueSendFromISR()` 解锁该任务时，FreeRTOS 会认为需要切换任务，`xHigherPriorityTaskWoken` 会被置为 `pdTRUE`，随后 `portYIELD_FROM_ISR()` 触发上下文切换。

如果 `vUartRxTask` 和当前被中断任务同优先级，`xTaskRemoveFromEventList()` 通常不会返回 `pdTRUE`，也就不会通过这条路径立即切到 RX 任务。

## 当前需要注意的问题

### 1. `xQueueCreate()` 需要检查返回值

当前代码：

```c
xUartRxQueue = xQueueCreate(64, sizeof(char));
```

没有检查返回值。FreeRTOS 的 `xQueueCreate()` 可能返回 `NULL`，表示队列创建失败。

当前 `FreeRTOSConfig.h` 没有定义有效的 `configASSERT()`，`FreeRTOS.h` 会把它定义为空宏。因此如果队列创建失败，后续：

```c
xQueueReceive(xUartRxQueue, &ch, portMAX_DELAY)
```

可能在空句柄上继续执行，风险比开启 assert 的配置更高。

建议后续改成：

```c
xUartRxQueue = xQueueCreate(64, sizeof(char));
if (xUartRxQueue == NULL) {
    debug_log("uart rx queue create failed\n");
    for (;;) {
    }
}
```

或者引入统一的 panic/assert 机制。

### 2. `debug_log()` 仍是最小 formatter

本次只补了 `%c`，没有实现完整格式控制。后续写日志时要避免：

```text
%02x
%lx
%u
```

除非继续扩展 `debug_log()` 的 parser。

当前推荐写法是：

```c
debug_log("rx: %x '%c'\n", (unsigned long)value, ch);
```

### 3. Queue 满时当前会静默丢字符

`xQueueSendFromISR()` 的返回值当前没有检查。如果 RX 输入很快，而消费任务来不及处理，64 字节 Queue 可能写满。写满后 `xQueueSendFromISR()` 会失败，当前代码会静默丢字符。

bring-up 阶段这可以接受，因为目标是验证 ISR 到任务唤醒路径。但如果后续要做可靠传输，需要至少统计丢包计数，或者改成 stream buffer / ring buffer。

### 4. ISR 中仍需避免复杂逻辑

当前 ISR 已经不再打印普通 RX 字符，这是正确方向。后续仍应保持 ISR 只做：

```text
claim
读取必要硬件状态
清除/解除设备中断条件
投递轻量事件
complete
yield if needed
```

复杂解析、日志、协议处理都应留给任务上下文。

## 本阶段总结

本次提交完成了从“中断链路能进 ISR”到“ISR 能唤醒 FreeRTOS 任务”的关键一步。

上一阶段验证的是：

```text
PLIC/UART2 external interrupt 能进入 handle_interrupt()
```

本阶段验证的是：

```text
handle_interrupt()
  -> FreeRTOS ISR-safe Queue API
  -> 高优先级任务解除阻塞
  -> portYIELD_FROM_ISR()
  -> 任务上下文处理 RX 字符
```

这条链路跑通后，后续可以把 UART2 字符事件替换成更接近 AMP 通信需求的 doorbell interrupt、共享内存 ring buffer 或 message queue。
