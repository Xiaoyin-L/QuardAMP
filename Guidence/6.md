# FreeRTOS PLIC 与 uart2 中断接入记录

本文承接 `5.md`，记录 FreeRTOS 在 `hart7` 上接入 S-mode external interrupt 的方案和当前实现进展。内容不只包含 PLIC driver，还包括 FreeRTOS trap 入口、`sie.SEIE`、uart2 设备侧 RX interrupt enable、DTS IRQ 同步，以及下一步验证计划。

当前 FreeRTOS 已经能依靠 SBI timer tick 正常调度任务，说明 S-mode trap 入口、timer interrupt、`vTaskDelay()` 和任务切换都已经工作。现在推进的目标是验证：

```text
uart2 / PLIC external interrupt
  -> hart7 S-mode external interrupt
  -> FreeRTOS trap entry
  -> handle_interrupt()
  -> plic_claim()
  -> plic_complete()
```

只有这条链路稳定后，后续做共享内存 ring buffer + doorbell/中断通知才会比较稳。

## 参考依据

本方案主要参考四处：

1. 本项目 `Guidence/5.md`

   `5.md` 已经确认 FreeRTOS 在 `hart7` 的 S-mode 能启动、SBI timer tick 能工作，并列出了 PLIC 的目标地址：

   ```text
   PLIC base        = 0x0c000000
   hart7 SENABLE    = 0x0c002780
   hart7 SPRIORITY  = 0x0c20f000
   hart7 SCLAIM     = 0x0c20f004
   ```

2. 本项目 `trusted_domain/driver/quard_star.h`

   当前已经定义了平台常量：

   ```c
   #define PRIM_HART 7UL
   #define UART2_IRQ 12
   #define PLIC_ADDR 0x0c000000UL
   #define PLIC_PRIORITY_BASE 0x000000UL
   #define PLIC_ENABLE_BASE 0x002000UL
   #define PLIC_CONTEXT_BASE 0x200000UL
   #define PLIC_ENABLE_STRIDE 0x80UL
   #define PLIC_CONTEXT_STRIDE 0x1000UL
   ```

   这里已经把 hart、UART IRQ 和 PLIC 布局集中到了板级头文件里，所以 PLIC driver 应该复用这些宏，而不是在 `plic.c` 里散落魔法数字。

3. 本项目 `xv6-riscv/kernel/plic.c`

   xv6 的 PLIC driver 是很好的最小参考：

   - `plicinit()` 设置设备 IRQ priority
   - `plicinithart()` 设置当前 hart 的 S-mode enable bit 和 threshold
   - `plic_claim()` 读取 claim 寄存器
   - `plic_complete()` 写回同一个 claim/complete 寄存器

   FreeRTOS 版本可以沿用这个结构，但固定面向 `hart7`，并且只启用 `uart2`。

## `plic.c` 的代码来源说明

`trusted_domain/driver/plic.c` 不是直接来自 FreeRTOS 官方，也不是来自 OpenSBI。它更准确地说是：

```text
参考 xv6-riscv 的 PLIC driver 结构
  + 结合 RISC-V PLIC 寄存器布局
  + 按 QuardAMP trusted_domain / hart7 / uart2 改写
```

原始参考文件是本仓库里的：

```text
xv6-riscv/kernel/plic.c
xv6-riscv/kernel/memlayout.h
```

xv6-riscv 属于 MIT xv6 教学操作系统体系，它的 PLIC driver 是一个非常小的 S-mode PLIC 驱动，核心逻辑就是：

```c
void plicinit(void);
void plicinithart(void);
int plic_claim(void);
void plic_complete(int irq);
```

本方案中的 `trusted_domain/driver/plic.c` 就是在这个 xv6 PLIC driver 思路上改的，不是照搬。主要修改点如下：

1. 去掉 xv6 的内核依赖

   xv6 版本依赖：

   ```c
   #include "types.h"
   #include "param.h"
   #include "memlayout.h"
   #include "riscv.h"
   #include "defs.h"
   ```

   FreeRTOS trusted_domain 不能依赖 xv6 的这些头文件，所以改成只依赖：

   ```c
   #include <stdint.h>
   #include "plic.h"
   #include "quard_star.h"
   ```

2. 去掉 `cpuid()`，固定到 `hart7`

   xv6 版本是多核 OS，所以 `plicinithart()`、`plic_claim()`、`plic_complete()` 都会通过：

   ```c
   int hart = cpuid();
   ```

   当前 FreeRTOS trusted_domain 只运行在：

   ```c
   #define PRIM_HART 7UL
   ```

   所以草案里直接推导：

   ```c
   #define PLIC_S_CONTEXT(hart) ((hart) * 2UL + 1UL)
   #define PLIC_HART7_S_CONTEXT PLIC_S_CONTEXT(PRIM_HART)
   ```

   这样目标 context 就是 hart7 的 S-mode context，即 context 15。

3. 从 xv6 的 `UART0_IRQ` / `VIRTIO0_IRQ` 改成 FreeRTOS 的 `UART2_IRQ`

   xv6 版本启用的是：

   ```c
   UART0_IRQ
   VIRTIO0_IRQ
   ```

   trusted_domain 的目标是让 FreeRTOS 独占 `uart2`，所以草案只启用：

   ```c
   UART2_IRQ
   ```

   这样可以避免 FreeRTOS 去处理 xv6 使用的 `uart0` 和 `virtio` 中断。

4. 把 xv6 的宏地址改成 QuardAMP 板级宏

   xv6 版本在 `memlayout.h` 中定义：

   ```c
   #define PLIC 0x0c000000L
   #define PLIC_SENABLE(hart) (PLIC + 0x2080 + (hart)*0x100)
   #define PLIC_SPRIORITY(hart) (PLIC + 0x201000 + (hart)*0x2000)
   #define PLIC_SCLAIM(hart) (PLIC + 0x201004 + (hart)*0x2000)
   ```

   trusted_domain 版本改为使用 `quard_star.h` 里的：

   ```c
   #define PLIC_ADDR 0x0c000000UL
   #define PLIC_PRIORITY_BASE 0x000000UL
   #define PLIC_ENABLE_BASE 0x002000UL
   #define PLIC_CONTEXT_BASE 0x200000UL
   #define PLIC_ENABLE_STRIDE 0x80UL
   #define PLIC_CONTEXT_STRIDE 0x1000UL
   ```

   这样 PLIC driver 和 QuardAMP 的平台配置保持一致。

5. 函数名改成更明确的 hart7 版本

   xv6 版本：

   ```c
   plicinit()
   plicinithart()
   plic_claim()
   plic_complete()
   ```

   trusted_domain 草案：

   ```c
   plic_init_hart7()
   plic_enable_irq_hart7()
   plic_claim_hart7()
   plic_complete_hart7()
   ```

   这样一眼能看出它现在不是通用 PLIC driver，而是阶段 2 bring-up 用的 hart7 专用实现。

所以可以在论文/报告/注释里这样描述：

```text
trusted_domain/driver/plic.c 参考 xv6-riscv 的 S-mode PLIC 驱动模型实现。
在 xv6 plicinit/plicinithart/plic_claim/plic_complete 的基础上，
去除了 xv6 内核头文件和 cpuid() 依赖，改为使用 QuardAMP trusted_domain
的板级常量，并固定配置 hart7 的 S-mode PLIC context，只启用 FreeRTOS
侧使用的 uart2 中断源。
```

4. RISC-V PLIC 常规寄存器布局

   QEMU virt / SiFive PLIC 常见布局如下：

   ```text
   priority[irq]        = PLIC_BASE + 0x000000 + irq * 4
   pending              = PLIC_BASE + 0x001000
   enable[context]      = PLIC_BASE + 0x002000 + context * 0x80
   threshold[context]   = PLIC_BASE + 0x200000 + context * 0x1000
   claim/complete       = PLIC_BASE + 0x200004 + context * 0x1000
   ```

   对于 QEMU virt 风格的 PLIC，每个 hart 通常有两个 context：

   ```text
   hart0 M-mode context = 0
   hart0 S-mode context = 1
   hart1 M-mode context = 2
   hart1 S-mode context = 3
   ...
   hart7 M-mode context = 14
   hart7 S-mode context = 15
   ```

   因此：

   ```text
   hart7 S-mode context = 7 * 2 + 1 = 15
   enable    = 0x0c000000 + 0x002000 + 15 * 0x80   = 0x0c002780
   threshold = 0x0c000000 + 0x200000 + 15 * 0x1000 = 0x0c20f000
   claim     = 0x0c000000 + 0x200004 + 15 * 0x1000 = 0x0c20f004
   ```

   这正好和 `5.md` 中记录的地址一致。

## 当前前置条件

### 1. OpenSBI domain 已经允许 trusted-domain 访问 PLIC

`dts/quard_star_sbi.dts` 中已有：

```dts
tplic: tplic {
    compatible = "opensbi,domain,memregion";
    base = <0x0 0x0c000000>;
    order = <22>;
    mmio;
};

tdomain: trusted-domain {
    regions = <&tmem 0x38>, <&tuart 0x18>, <&tplic 0x18>;
};
```

所以阶段 2 不需要重复加 PLIC domain region。后续如果访问 PLIC 时出现 OpenSBI domain access fault，再回头查 DTS 编译和 `fw.bin` 打包链路。

### 2. `Makefile` 会自动编译 `driver/*.c`

`trusted_domain/Makefile` 当前的 `C_SOURCES` 已经包含：

```make
${wildcard $(TOP_DIR)/driver/*.c}
```

所以新建 `trusted_domain/driver/plic.c` 后，不需要额外把它手动加进 Makefile。

### 3. 当前 FreeRTOS 还没有打开 S-mode external interrupt

`trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/port.c` 当前只打开了：

```c
csr_set(CSR_SIE, SIP_STIP);
csr_set(CSR_SIE, SIP_SSIP);
```

这里需要再加：

```c
csr_set(CSR_SIE, SIP_SEIP);
```

原因是 PLIC 发给 S-mode 的外部中断最终表现为 `scause = 0x8000000000000009`，也就是 Supervisor external interrupt。不开 `sie.SEIE`，PLIC pending 了也不会进入 FreeRTOS trap。

### 4. 当前 `handle_interrupt` 是弱定义死循环

`trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/portASM.S` 里有：

```asm
.weak handle_interrupt

handle_interrupt:
    j handle_interrupt
```

这表示如果我们不提供强符号 `handle_interrupt()`，一旦外部中断发生，系统会卡死。因此 PLIC driver 接入时必须同时提供一个 C 版本：

```c
void handle_interrupt(void);
```

## 重要风险：uart2 IRQ 需要确认

当前 `trusted_domain/driver/quard_star.h` 写的是：

```c
#define UART2_IRQ 12
```

但 `dts/quard_star_sbi.dts` 里 `uart2` 当前还是：

```dts
uart2: uart2@10002000 {
    interrupts = <0xa>;
};
```

也就是 IRQ 10。

这两者不一致。后续验证前必须确认 QEMU 板级代码里 `uart2` 真实接到哪个 PLIC source：

- 如果 QEMU 真实硬件把 `uart2` 接到 IRQ 12，那么 DTS 应该同步改成 `<0xc>`。
- 如果 QEMU 真实硬件仍把 `uart2` 接到 IRQ 10，那么 `UART2_IRQ` 应该暂时改成 10，但这会和 xv6 的 `uart0` 抢同一个 IRQ，不推荐。

阶段 2 的 driver 先按项目目标 `UART2_IRQ = 12` 写。验证前建议先查 QEMU board 或实测 claim 出来的 IRQ 值。

## 文件 1：`trusted_domain/driver/plic.h`

代码草案：

```c
#ifndef PLIC_H
#define PLIC_H

/*
 * 初始化 hart7 的 S-mode PLIC context。
 *
 * 这个函数只负责 PLIC 本身：
 * - 设置 hart7 S-mode threshold
 * - 可选清理 enable 寄存器
 *
 * 它不负责打开 CPU 的 sie.SEIE，也不负责初始化 uart2。
 */
void plic_init_hart7(void);

/*
 * 启用某个 PLIC interrupt source。
 *
 * irq 是 PLIC source ID，例如 UART2_IRQ。
 * PLIC 的 source 0 表示 no interrupt，不能作为真实设备 IRQ 使用。
 */
void plic_enable_irq_hart7(int irq);

/*
 * 从 hart7 S-mode claim/complete 寄存器读取当前待处理 IRQ。
 *
 * 返回值：
 * - 0：没有 pending external interrupt
 * - >0：具体 PLIC source ID
 */
int plic_claim_hart7(void);

/*
 * 告诉 PLIC 某个 IRQ 已经处理完成。
 *
 * PLIC 要求把 claim 得到的同一个 IRQ ID 写回 claim/complete 寄存器。
 * 如果不 complete，同一个设备后续可能无法再次触发中断。
 */
void plic_complete_hart7(int irq);

#endif
```

## 文件 2：`trusted_domain/driver/plic.c`

代码草案：

```c
#include <stdint.h>
#include "plic.h"
#include "quard_star.h"

/*
 * PLIC MMIO 寄存器是 32-bit 宽度。
 *
 * 使用 volatile 的原因：
 * - 这些地址不是普通内存，而是设备寄存器。
 * - 编译器不能缓存读写，也不能把看似无用的读写优化掉。
 */
static inline volatile uint32_t *plic_reg(unsigned long offset)
{
    return (volatile uint32_t *)(PLIC_ADDR + offset);
}

/*
 * QEMU virt / SiFive PLIC 常见 context 编号：
 *
 *   hart0 M-mode = 0
 *   hart0 S-mode = 1
 *   hart1 M-mode = 2
 *   hart1 S-mode = 3
 *   ...
 *
 * 所以 hart7 S-mode = 7 * 2 + 1 = 15。
 *
 * 这里不直接写 15，而是从 PRIM_HART 推导，避免以后调整 trusted hart
 * 时忘记同步 context 编号。
 */
#define PLIC_S_CONTEXT(hart) ((hart) * 2UL + 1UL)
#define PLIC_HART7_S_CONTEXT PLIC_S_CONTEXT(PRIM_HART)

/*
 * priority 寄存器：
 * - 每个 IRQ source 一个 32-bit priority
 * - priority = 0 表示该 source 被 PLIC 层面禁用
 * - priority > threshold 才能投递给目标 context
 */
#define PLIC_PRIORITY(irq) \
    (PLIC_PRIORITY_BASE + ((unsigned long)(irq) * 4UL))

/*
 * enable 寄存器：
 * - 每个 context 有一组 enable bits
 * - 每 32 个 IRQ source 占用一个 32-bit enable word
 * - context 之间的 stride 是 0x80
 */
#define PLIC_ENABLE(context, irq) \
    (PLIC_ENABLE_BASE + ((context) * PLIC_ENABLE_STRIDE) + \
     (((unsigned long)(irq) / 32UL) * 4UL))

/*
 * threshold 寄存器：
 * - priority 必须大于 threshold 才会被投递
 * - 设置为 0 表示允许所有 priority >= 1 的中断进来
 */
#define PLIC_THRESHOLD(context) \
    (PLIC_CONTEXT_BASE + ((context) * PLIC_CONTEXT_STRIDE))

/*
 * claim/complete 是同一个寄存器：
 * - 读：claim 一个当前最高优先级 pending IRQ
 * - 写：complete 对应 IRQ
 */
#define PLIC_CLAIM(context) \
    (PLIC_CONTEXT_BASE + ((context) * PLIC_CONTEXT_STRIDE) + 4UL)

static void plic_set_priority(int irq, uint32_t priority)
{
    if (irq <= 0) {
        return;
    }

    *plic_reg(PLIC_PRIORITY(irq)) = priority;
}

void plic_init_hart7(void)
{
    const unsigned long context = PLIC_HART7_S_CONTEXT;

    /*
     * threshold = 0：
     * 只要某个 IRQ source 的 priority 设置为 1 或更高，就可以投递。
     */
    *plic_reg(PLIC_THRESHOLD(context)) = 0;

    /*
     * 先把 UART2 的 priority 设为 1。
     *
     * 更完整的版本可以在这里统一初始化所有 trusted-domain 使用的 IRQ。
     * 当前阶段只验证 uart2，所以保持最小。
     */
    plic_set_priority(UART2_IRQ, 1);
}

void plic_enable_irq_hart7(int irq)
{
    const unsigned long context = PLIC_HART7_S_CONTEXT;
    volatile uint32_t *enable;
    uint32_t bit;

    if (irq <= 0) {
        return;
    }

    enable = plic_reg(PLIC_ENABLE(context, irq));
    bit = (uint32_t)(1UL << ((unsigned long)irq % 32UL));
    *enable = *enable | bit;
}

int plic_claim_hart7(void)
{
    const unsigned long context = PLIC_HART7_S_CONTEXT;

    return (int)(*plic_reg(PLIC_CLAIM(context)));
}

void plic_complete_hart7(int irq)
{
    const unsigned long context = PLIC_HART7_S_CONTEXT;

    if (irq <= 0) {
        return;
    }

    *plic_reg(PLIC_CLAIM(context)) = (uint32_t)irq;
}
```

### 为什么这样写

1. 固定使用 hart7 S-mode context

   当前 trusted-domain 只跑在 `PRIM_HART = 7`，没必要先做通用多核 PLIC driver。固定 hart7 可以减少变量，降低调试复杂度。

2. 用 `quard_star.h` 的平台宏

   PLIC base、stride、UART IRQ 已经在板级头文件中定义。driver 复用这些宏，以后如果硬件布局变化，只改平台头文件即可。

3. `priority` 和 `enable` 分开设置

   PLIC 必须同时满足：

   ```text
   priority[irq] > threshold[context]
   enable[context][irq] = 1
   ```

   只设置 enable 不设置 priority，中断仍然不会投递。

4. 先检查 IRQ，再计算 enable 地址

   `plic_enable_irq_hart7()` 中不能在检查 `irq` 之前就计算 enable 寄存器地址：

   ```c
   volatile uint32_t *enable = plic_reg(PLIC_ENABLE(context, irq));
   ```

   原因是 `PLIC_ENABLE(context, irq)` 会把 `irq` 参与地址计算。如果 `irq` 是负数，转换成 `unsigned long` 后会变成很大的值，算出的 MMIO 地址没有意义。更稳的顺序是：

   ```c
   if (irq <= 0) {
       return;
   }

   enable = plic_reg(PLIC_ENABLE(context, irq));
   ```

5. claim 后必须 complete

   PLIC 的处理模型是 claim/complete。handler 读出 IRQ 后，如果不写回 complete，同一个 source 可能保持忙状态，后续中断进不来。

## 文件 3：新增 `trusted_domain/driver/irq.c`

建议把 `handle_interrupt()` 放到独立文件，而不是塞进 `plic.c`。原因是：

- `plic.c` 只负责 PLIC 寄存器操作。
- `irq.c` 负责平台中断分发。
- 后续要分发 uart2、共享内存 doorbell、其他设备 IRQ 时结构更清楚。

代码草案：

```c
#include "debug_log.h"
#include "plic.h"
#include "quard_star.h"

/*
 * FreeRTOS RISC-V portASM.S 中声明了 weak handle_interrupt。
 *
 * 这里提供同名强符号后，链接器会选择本函数。
 * 当 scause 是 Supervisor external interrupt 时，portASM.S 会跳到这里。
 */
void handle_interrupt(void)
{
    int irq = plic_claim_hart7();

    if (irq == 0) {
        return;
    }

    /*
     * 第一阶段先只打印和 complete，确认中断链路能跑通。
     *
     * 注意：
     * debug_log 是 polling UART 输出。短日志可以用于 bring-up，
     * 但正式 ISR 中不建议大量打印，否则会拉长中断处理时间。
     */
    if (irq == UART2_IRQ) {
        debug_log("plic: uart2 irq %d\n", irq);
    } else {
        debug_log("plic: unknown irq %d\n", irq);
    }

    plic_complete_hart7(irq);
}
```

### 为什么先用 `debug_log`

阶段 2 的目标是 bring-up，不是性能优化。此时最重要的是知道：

```text
外部中断有没有进入 FreeRTOS
claim 出来的 IRQ ID 是多少
complete 后系统会不会继续调度
```

所以短暂使用 polling log 是可以接受的。等路径确认后，再把 ISR 改成只读 UART 寄存器、投递队列或 task notification。

## 文件 4：修改 `port.c` 打开 SEIE

位置：

```text
trusted_domain/FreeRTOS-Kernel/portable/GCC/RISC-V/port.c
```

当前：

```c
csr_set(CSR_SIE, SIP_STIP);
csr_set(CSR_SIE, SIP_SSIP);
```

建议改为：

```c
/*
 * 打开 S-mode 可响应的中断类型。
 *
 * SIP_STIP：Supervisor timer interrupt，由 SBI set_timer 触发，用作 FreeRTOS tick。
 * SIP_SSIP：Supervisor software interrupt，后续可用于 IPI/yield。
 * SIP_SEIP：Supervisor external interrupt，由 PLIC 投递，例如 uart2 IRQ。
 *
 * 这里打开的是 sie 中的局部中断使能位；真正的全局 SIE 位会在
 * xPortStartFirstTask() 恢复第一个任务上下文时打开。
 */
csr_set(CSR_SIE, SIP_STIP);
csr_set(CSR_SIE, SIP_SSIP);
csr_set(CSR_SIE, SIP_SEIP);
```

### 为什么不是在 `main()` 里直接开

FreeRTOS RISC-V port 已经集中负责 scheduler 启动前的 trap/timer/interrupt 初始化。把 `SIP_SEIP` 放在 `xPortStartScheduler()` 中，语义更一致：

```text
port.c 负责 CPU interrupt enable
plic.c 负责 interrupt controller enable
uart/ns16550.c 负责设备侧 interrupt enable
```

这样后续排查问题时边界比较清楚。

## 文件 5：修改 `main.c` 初始化顺序

位置：

```text
trusted_domain/main.c
```

建议在启动 scheduler 前初始化 UART 和 PLIC：

```c
#include <FreeRTOS.h>
#include <task.h>
#include "debug_log.h"
#include "plic.h"
#include "quard_star.h"

int main(void)
{
    /*
     * debug_log 依赖 uart2 polling 输出，所以必须先初始化。
     */
    debug_log_init();
    debug_log("Hello FreeRTOS!\n");

    /*
     * PLIC 初始化要早于打开 S-mode external interrupt。
     * xPortStartScheduler() 中打开 sie.SEIE 后，PLIC pending 的外部中断
     * 就可能进入 handle_interrupt()。
     */
    plic_init_hart7();
    plic_enable_irq_hart7(UART2_IRQ);

    xTaskCreate(vTaskCreate, "task creat", 256, NULL, 4, NULL);

    vTaskStartScheduler();
    return 0;
}
```

同时把任务日志从：

```c
debug_log("task1 0x%x\n", time++);
debug_log("task2 0x%x\n", time++);
```

改为：


因为 `debug_log()` 的 `%x` 内部已经会输出 `0x` 前缀。

## 文件 6：启用 uart2 设备侧 RX 中断

PLIC 只是中断控制器。要让 uart2 真正产生外部中断，还需要在 NS16550 设备侧打开 IER。

当前 `trusted_domain/driver/ns16550.c` 可以在保留 polling 输出的基础上，增加 RX interrupt enable 和非阻塞读接口：

```c
#define UART_RHR 0
#define UART_THR 0
#define UART_IER 1
#define UART_FCR 2
#define UART_LCR 3
#define UART_LSR 5
#define UART_IER_RDA 0x01
#define UART_FCR_FIFO_ENABLE 0x01
#define UART_FCR_CLEAR_RCVR 0x02
#define UART_FCR_CLEAR_XMIT 0x04
#define UART_LCR_8N1 0x03
#define UART_LSR_DR 0x01
#define UART_LSR_THRE 0x20

void ns16550_init(void)
{
    /*
     * 启动阶段先关闭设备侧中断，避免 PLIC/handler 尚未准备好时
     * UART 已经产生 RX interrupt。
     */
    uart[UART_IER] = 0;

    /*
     * 8 data bits, no parity, 1 stop bit。
     * 这里只设置基本帧格式，不改 baud divisor，避免破坏 QEMU 已经可用的串口输出。
     */
    uart[UART_LCR] = UART_LCR_8N1;

    /*
     * 打开 FIFO，并清掉启动前残留的 RX/TX FIFO 内容。
     */
    uart[UART_FCR] = UART_FCR_FIFO_ENABLE | UART_FCR_CLEAR_RCVR |
                     UART_FCR_CLEAR_XMIT;
}

void ns16550_enable_rx_irq(void)
{
    /*
     * NS16550 IER bit0 = Received Data Available Interrupt Enable。
     * 打开后，RX FIFO 有数据时 UART 会向 PLIC 拉起对应 IRQ source。
     */
    uart[UART_IER] = uart[UART_IER] | UART_IER_RDA;
}

int ns16550_getc_nonblock(void)
{
    /*
     * LSR bit0 = Data Ready。
     * 没有输入字符时立即返回 -1，不在 ISR 里等待。
     */
    if ((uart[UART_LSR] & UART_LSR_DR) == 0) {
        return -1;
    }

    /*
     * 读取 RHR 会取走一个 RX 字符，也会帮助清除 UART 的 RX interrupt 条件。
     */
    return (int)uart[UART_RHR];
}
```

对应头文件 `trusted_domain/driver/ns16550.h` 增加：

```c
void ns16550_enable_rx_irq(void);
int ns16550_getc_nonblock(void);
```

### 为什么 ISR 里要读 RX 数据

UART RX interrupt 的触发条件通常是 RX FIFO 中有数据。如果 `handle_interrupt()` 只是 `plic_claim()` / `plic_complete()`，但不读取 `UART_RHR`，UART 设备侧的中断条件仍然存在。结果是 PLIC complete 后，同一个 external interrupt 很可能马上再次 pending，系统会反复进入 ISR。

所以 UART2 IRQ 的最小 handler 应该先读掉 RX FIFO：

```c
if (irq == UART2_IRQ) {
    debug_log("plic: uart2 irq %d\n", irq);
    while (ns16550_getc_nonblock() >= 0) {
    }
}
```

当前阶段只 drain 输入，不处理输入内容。后续需要真实通信时，再把读到的字符写入 ring buffer、queue 或 task notification。

## 排错顺序

### 现象 1：一开 SEIE 系统卡死

最可能原因：

```text
外部中断进来了，但 handle_interrupt 没有正确覆盖 weak 死循环
```

检查：

```sh
riscv64-unknown-elf-nm trusted_domain/build/trusted_fw.elf | grep handle_interrupt
```

应该看到 `handle_interrupt` 来自 `irq.o`，而不是只有 weak 符号。

### 现象 2：没有任何 uart2 irq 日志

按顺序检查：

1. `port.c` 是否打开 `SIP_SEIP`
2. `plic_init_hart7()` 是否设置 `threshold = 0`
3. `plic_enable_irq_hart7(UART2_IRQ)` 是否执行
4. `UART2_IRQ` 是否和 QEMU 真实 IRQ source 一致
5. uart2 设备侧 IER 是否打开

### 现象 3：claim 出来的是 IRQ 10

说明当前串口中断源仍然是 10。此时不要直接让 FreeRTOS 和 xv6 都处理 IRQ 10，应该统一硬件/DTS/平台头文件，目标仍建议保持：

```text
uart0 -> IRQ 10 -> xv6
uart2 -> IRQ 12 -> FreeRTOS
```

### 现象 4：第一次中断后再也没有第二次

最可能原因：

```text
claim 后没有 complete
```

确认 `handle_interrupt()` 最后执行：

```c
plic_complete_hart7(irq);
```

下一步优先做运行验证，而不是继续扩展功能。建议按这个顺序：

2. 启动 QEMU

   ```sh
   ./run.sh
   ```

   当前 `run.sh` 给 uart0/uart1/uart2 都配置为 `vc:960x480`。理论上第三个 serial 窗口对应 uart2，也就是 FreeRTOS 的输出和输入通道。

3. 在 serial2 输入任意字符

   预期 FreeRTOS 侧出现：

   ```text
   plic: uart2 irq 12
   ```

   如果 task1/task2 仍持续输出，说明中断处理后系统还能继续调度，`claim/complete` 路径基本正常。

4. 如果没有看到 `plic: uart2 irq 12`

   先不要改共享内存通信。优先检查 serial2 是否真的可输入。必要时把 `run.sh` 的第三个串口临时改成文件、PTY 或 stdio 方案，例如给 uart2 单独分配一个更容易输入的后端。

   下一阶段是把当前 ISR 从 bring-up 日志改成真正的 FreeRTOS 事件路径：

   ```text
   uart2 irq
     -> ns16550_getc_nonblock()
     -> 写入 RX ring buffer 或 FreeRTOS queue
     -> xTaskNotifyGiveFromISR() / xQueueSendFromISR()
     -> 必要时触发 ISR 后任务切换
   ```

   做完这个后，再进入 xv6-FreeRTOS 共享内存 ring buffer。这样顺序更稳：先证明外部中断可靠，再把中断转成任务级处理，最后做跨系统通信。
