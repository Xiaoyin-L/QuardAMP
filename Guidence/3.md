# OpenSBI 启动后无输出/卡死问题记录

## 现象

运行项目：

```shell
./run.sh
```

终端可以看到 OpenSBI banner 和平台信息，但在 OpenSBI 输出结束后没有任何后续日志，看起来像 QEMU 卡死。

清除测试 payload 后，当前现象应为：

1. 能正常看到 OpenSBI 输出。
2. 能看到 `Domain0 Next Address : 0x0000000080200000`。
3. OpenSBI 跳到 `0x80200000` 后不再有输出。

第 3 点是正常的，因为当前项目里还没有真正的 S-mode 程序，例如 xv6、FreeRTOS 或其他内核，被放到 `0x80200000`。

## 原因

这次问题的核心不是 QEMU 本身卡死，而是启动链路没有把 OpenSBI 的下一阶段配置完整。

启动链路应为：

```text
MROM -> lowlevelboot -> OpenSBI -> S-mode 程序
```

其中：

1. `lowlevelboot` 从 pflash 拷贝 OpenSBI 到 DDR 的 `0x80000000`。
2. `lowlevelboot` 从 pflash 拷贝 DTB 到 DDR 的 `0x82200000`。
3. `lowlevelboot` 将 `a0=hartid`、`a1=0x82200000` 传给 OpenSBI。
4. OpenSBI 初始化完成后，按 `FW_JUMP_ADDR` 跳到下一阶段 S-mode 程序。

原问题里 OpenSBI 的 `FW_JUMP_ADDR` 没有正确配置到 `0x80200000`，甚至出现过 `Domain0 Next Address : 0x0000000000000000`。这样 OpenSBI 打印完自身日志后会跳到错误地址，后面自然没有任何有效输出。

同时，项目当前还没有真正的 S-mode 内核镜像。因此即使把 OpenSBI 的 `Next Address` 修正为 `0x80200000`，如果该地址没有放 xv6/FreeRTOS/kernel，OpenSBI 后面仍然不会继续打印。这不是 OpenSBI 没启动，而是下一阶段程序还没接上。

## 启动链在哪里指明

这条启动链：

```text
MROM -> lowlevelboot -> OpenSBI -> S-mode 程序
```

不是在一个文件里集中声明的，而是由 QEMU、链接脚本、`build.sh`、BL1 汇编和 OpenSBI 固件参数一起拼出来的。

### MROM 到 lowlevelboot

MROM 是 QEMU 模拟出来的。相关代码在：

```text
qemu-10.2.4/hw/riscv/quard_star.c
```

其中 `quard_star_setup_rom_reset_vec()` 会生成 CPU 复位后的 reset vector：

```c
quard_star_setup_rom_reset_vec(machine, &s->soc[0],
                              virt_memmap[QUARD_STAR_FLASH].base,
                              virt_memmap[QUARD_STAR_MROM].base,
                              virt_memmap[QUARD_STAR_MROM].size,
                              0x0, 0x0);
```

`virt_memmap[QUARD_STAR_FLASH].base` 是 pflash 基地址：

```c
[QUARD_STAR_FLASH] = { 0x20000000, 0x2000000 },
```

所以 CPU 复位后，QEMU 的 MROM 会跳到 `0x20000000`。

`lowlevelboot/boot.lds` 又把 lowlevelboot 链接到 `0x20000000`：

```ld
ENTRY(_start)

MEMORY
{
    flash (rxai!w) : ORIGIN = 0x20000000, LENGTH = 512k
}
```

因此：

```text
MROM reset vector -> 0x20000000 -> lowlevelboot/startup.s:_start
```

### lowlevelboot 到 OpenSBI

`lowlevelboot/startup.s` 负责把 OpenSBI 从 pflash 拷贝到 DDR：

```asm
//load opensbi_fw.bin
//[0x20200000:0x20400000] --> [0x80000000:0x80200000]
li      a0, 0x202
slli    a0, a0, 20      //a0 = 0x20200000
li      a1, 0x800
slli    a1, a1, 20      //a1 = 0x80000000
li      a2, 0x802
slli    a2, a2, 20      //a2 = 0x80200000
load_data a0,a1,a2
```

然后把 DTB 从 pflash 拷贝到 DDR：

```asm
//load qemu_sbi.dtb
//[0x20080000:0x20100000] --> [0x82200000:0x82280000]
li      a0, 0x2008
slli    a0, a0, 16      //a0 = 0x20080000
li      a1, 0x822
slli    a1, a1, 20      //a1 = 0x82200000
li      a2, 0x8228
slli    a2, a2, 16      //a2 = 0x82280000
load_data a0,a1,a2
```

最后把 DTB 地址放进 `a1`，跳到 OpenSBI 入口：

```asm
li      a1, 0x822
slli    a1, a1, 20      //a1 = 0x82200000
li      t0, 0x800
slli    t0, t0, 20      //t0 = 0x80000000
jr      t0
```

RISC-V 启动约定里，进入下一阶段时通常：

```text
a0 = hart id
a1 = DTB 地址
```

这里 `a0` 来自前面的：

```asm
csrr a0, mhartid
```

所以：

```text
lowlevelboot -> 0x80000000 -> OpenSBI
```

### OpenSBI 到 S-mode 程序

OpenSBI 使用 `fw_jump` 固件时，下一阶段入口由 `FW_JUMP_ADDR` 决定。

项目里的配置在：

```text
opensbi/platform/quard_star/objects.mk
```

当前配置是：

```makefile
FW_JUMP=y
FW_TEXT_START=0x80000000
FW_JUMP_ADDR=0x80200000
FW_JUMP_FDT_ADDR=0x82200000
```

含义：

| 参数 | 含义 |
| --- | --- |
| `FW_TEXT_START=0x80000000` | OpenSBI 自己运行在 DDR 的 `0x80000000` |
| `FW_JUMP_ADDR=0x80200000` | OpenSBI 初始化完成后跳到 `0x80200000` |
| `FW_JUMP_FDT_ADDR=0x82200000` | OpenSBI 传给 S-mode 程序的 DTB 地址 |

OpenSBI 源码里读取 `FW_JUMP_ADDR` 的位置在：

```text
opensbi/firmware/fw_jump.S
```

关键逻辑：

```asm
fw_next_addr:
#ifdef FW_JUMP_ADDR
    lla a0, _jump_addr
    REG_L a0, (a0)
#elif defined(FW_JUMP_OFFSET)
    lla a0, _fw_start
    li  a1, FW_JUMP_OFFSET
    add a0, a0, a1
#else
#error "Must define at least FW_JUMP_ADDR or FW_JUMP_OFFSET"
#endif
    ret
```

所以：

```text
OpenSBI -> FW_JUMP_ADDR -> 0x80200000 -> S-mode 程序
```

当前没有真正的 S-mode 程序放在 `0x80200000`，因此 OpenSBI 输出结束后不会再有新日志。

### fw.bin 里的布局

最终 QEMU 启动时加载的是：

```text
output/fw/fw.bin
```

`run.sh` 通过 pflash 挂载它：

```shell
-drive if=pflash,bus=0,unit=0,format=raw,file=$SHELL_FOLDER/output/fw/fw.bin
```

QEMU 里 pflash 基地址是：

```text
0x20000000
```

`build.sh` 负责把各阶段写进 `fw.bin`：

```shell
dd of=fw.bin bs=1k count=32k if=/dev/zero
dd of=fw.bin bs=1k conv=notrunc seek=0 if=$SHELL_FOLDER/output/lowlevelboot/lowlevel_fw.bin
dd of=fw.bin bs=1k conv=notrunc seek=512 if=$SHELL_FOLDER/output/opensbi/quard_star_sbi.dtb
dd of=fw.bin bs=1k conv=notrunc seek=2K if=$SHELL_FOLDER/output/opensbi/fw_jump.bin
```

因为 `bs=1k`，所以布局是：

| `fw.bin` 偏移 | pflash 地址 | 内容 |
| --- | --- | --- |
| `0 KiB` | `0x20000000` | lowlevelboot |
| `512 KiB` | `0x20080000` | DTB |
| `2048 KiB` | `0x20200000` | OpenSBI `fw_jump.bin` |

再结合 `startup.s` 的拷贝逻辑：

| pflash 地址 | DDR 地址 | 内容 |
| --- | --- | --- |
| `0x20200000` | `0x80000000` | OpenSBI |
| `0x20080000` | `0x82200000` | DTB |

所以当前完整启动关系是：

```text
QEMU MROM
  -> 0x20000000
  -> lowlevelboot
  -> copy OpenSBI: 0x20200000 -> 0x80000000
  -> copy DTB:     0x20080000 -> 0x82200000
  -> jr 0x80000000
  -> OpenSBI
  -> FW_JUMP_ADDR 0x80200000
  -> S-mode 程序
```

## 修复思路

修复分成两件事：

1. 让 OpenSBI 自身在正确的 DDR 地址运行。
2. 让 OpenSBI 明确知道下一阶段入口地址和 DTB 地址。

关键配置：

```makefile
FW_JUMP=y
FW_TEXT_START=0x80000000
FW_JUMP_ADDR=0x80200000
FW_JUMP_FDT_ADDR=0x82200000
```

含义：

| 配置 | 含义 |
| --- | --- |
| `FW_JUMP=y` | 构建 OpenSBI 的 `fw_jump.bin` 固件 |
| `FW_TEXT_START=0x80000000` | OpenSBI 运行基地址 |
| `FW_JUMP_ADDR=0x80200000` | OpenSBI 完成初始化后跳转的 S-mode 入口 |
| `FW_JUMP_FDT_ADDR=0x82200000` | OpenSBI 传给 S-mode 程序的 DTB 地址 |

注意：参考教程时，OpenSBI 平台参数应写在 `opensbi/platform/quard_star/objects.mk`。这个文件会被 OpenSBI 顶层 Makefile include。

另外，实际构建中发现 `FW_TEXT_START` 这类变量变化不一定触发 OpenSBI 增量重建链接脚本。为了避免旧产物残留，`build.sh` 里也显式把这些参数传给 `make`。

## 修改的文件

### `opensbi/platform/quard_star/objects.mk`

加入 OpenSBI 固件构建参数：

```makefile
platform-objs-y += platform.o

FW_JUMP=y

# OpenSBI runs from DRAM after lowlevelboot copies it from pflash.
FW_TEXT_START=0x80000000

# The next S-mode stage is copied by lowlevelboot to this address.
FW_JUMP_ADDR=0x80200000
FW_JUMP_FDT_ADDR=0x82200000
```

作用：

1. 生成 `fw_jump.bin`。
2. 指定 OpenSBI 运行在 `0x80000000`。
3. 指定 OpenSBI 下一阶段跳到 `0x80200000`。
4. 指定传给下一阶段的 DTB 地址是 `0x82200000`。

### `build.sh`

主要改动：

1. 固定交叉编译器前缀：

```shell
CROSS_PREFIX=/opt/riscv64-lp64d--glibc--stable-2025.08-1/bin/riscv64-linux
```

2. 编译 OpenSBI 时显式传入地址参数：

```shell
make CROSS_COMPILE=$CROSS_PREFIX- PLATFORM=quard_star FW_TEXT_START=0x80000000 FW_JUMP_ADDR=0x80200000 FW_JUMP_FDT_ADDR=0x82200000
```

3. 生成 DTB：

```shell
dtc -I dts -O dtb -o $SHELL_FOLDER/output/opensbi/quard_star_sbi.dtb quard_star_sbi.dts
```

4. 合成最终 pflash 固件：

```shell
dd of=fw.bin bs=1k count=32k if=/dev/zero
dd of=fw.bin bs=1k conv=notrunc seek=0 if=$SHELL_FOLDER/output/lowlevelboot/lowlevel_fw.bin
dd of=fw.bin bs=1k conv=notrunc seek=512 if=$SHELL_FOLDER/output/opensbi/quard_star_sbi.dtb
dd of=fw.bin bs=1k conv=notrunc seek=2K if=$SHELL_FOLDER/output/opensbi/fw_jump.bin
```

当前没有测试 payload 写入步骤。

### `lowlevelboot/startup.s`

加入通用拷贝宏：

```asm
	.macro load_data,_src_start,_dst_start,_dst_end
	bgeu	\_dst_start, \_dst_end, 2f
1:
	lw      t0, (\_src_start)
	sw      t0, (\_dst_start)
	addi    \_src_start, \_src_start, 4
	addi    \_dst_start, \_dst_start, 4
	bltu    \_dst_start, \_dst_end, 1b
2:
	.endm
```

拷贝 OpenSBI：

```asm
	//[0x20200000:0x20400000] --> [0x80000000:0x80200000]
```

拷贝 DTB：

```asm
	//[0x20080000:0x20100000] --> [0x82200000:0x82280000]
```

最后跳到 OpenSBI：

```asm
    li		a1,	0x822
	slli	a1,	a1, 20       //a1 = 0x82200000
    li	    t0,	0x800
	slli	t0,	t0, 20       //t0 = 0x80000000
    jr      t0
```

作用：

1. `a0` 保持当前 hart id。
2. `a1` 传入 DTB 地址。
3. `jr t0` 跳入 OpenSBI 入口。



这说明：

1. `lowlevelboot` 已经成功跳入 OpenSBI。

当前没有后续输出，是因为还没有真正的 S-mode 程序放在 `0x80200000`。

## 后续如何接真正内核

后续如果要接 xv6、FreeRTOS 或其他 S-mode 程序，需要做两件事：

1. 将内核镜像链接入口设置为 `0x80200000`。
2. 在 `build.sh` 和 `lowlevelboot/startup.s` 中加入内核镜像写入和拷贝逻辑。

例如设计为：

```text
pflash 0x20400000 -> DDR 0x80200000
```

那么需要：

1. `build.sh` 把内核二进制写入 `fw.bin` 的某个偏移。
2. `lowlevelboot/startup.s` 把该偏移处的数据搬到 `0x80200000`。
3. OpenSBI 的 `FW_JUMP_ADDR` 保持 `0x80200000`。

这样 OpenSBI 输出结束后，就会进入真正的 S-mode 内核。
