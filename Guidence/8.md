# Benchtest 与 Buddy/Slab 性能指标更新

本文汇总飞书 Wiki 根文档及相关子文档中的最新结论：

- `ICC 性能基准测试`
- `rpmsg 标准化改进：used ring 回收与描述符空闲池`
- `buddy+slab内存管理适配`

重点记录当前 `benchtest` 的测试口径、rpmsg 改进后的对比指标，以及 xv6 中 Buddy 页面分配器和 Slab/SLUB 风格小对象分配器的可量化效果。

## 1. benchtest 测试口径

当前 `xv6-riscv/user/benchtest.c` 已经从单一 RPC 往返测试扩展为四类指标：

| 测试项 | 口径 | 目的 |
|-|-|-|
| Test 1 RPC Round-Trip Time | 20 次预热 + 200 次采样，统计 min/max/avg/p50/p99 和 jitter | 衡量同步 RPC 往返延迟 |
| Test 2 Latency Breakdown | bench endpoint 回传 FreeRTOS 侧 `t_rx/t_tx`，拆成 forward/handler/return | 定位耗时主要发生在去程、handler 还是回程 |
| Test 3 Ping-Pong Throughput | 1000 次 64B 同步 request/reply | 衡量单条在途同步吞吐上限 |
| Test 4 Batched In-Flight Throughput | 512 条消息，window=8，批量发送后逐个接收 | 衡量批量 avail 发布和通知合并的吞吐收益 |

计时统一使用 `rdtime`，当前 timebase 为 10MHz，即 100ns 粒度。QEMU TCG 下 `rdcycle` 不适合作为真实性能口径，因此 benchtest 用 `rdtime` 作为 xv6 与 FreeRTOS 两侧可比较的统一时间源。

## 2. ICC/rpmsg 基线指标

早期 ICC 基线环境：

```text
QEMU quard-star
8 hart: hart0-hart6 -> xv6, hart7 -> FreeRTOS
shared memory: 1MiB
virtio split ring + 512B buffer
QUARDAMP_DEMO=0
ICC_VERBOSE=0
```

早期基线实测：

| 指标 | min | max | avg | p50 | p99 |
|-|-|-|-|-|-|
| rpc_rtt | 2059us | 13663us | 6348us | 5984us | 13092us |
| forward_latency | 123us | 9641us | 441us | 260us | 6050us |
| handler_time | 4us | 252us | 11us | 9us | 86us |
| return_latency | 1464us | 13033us | 6362us | 5911us | 12601us |

同步 ping-pong 吞吐：

```text
1000 msgs, 64B each, 7087538us
rate=141 msg/s
bandwidth=8 KB/s
```

这组数据说明 handler 本身很轻，主要耗时集中在 `return_latency`，也就是 FreeRTOS 已发布回复后，xv6 用户态被唤醒并拿到结果的路径。

## 3. 日志静默后的 benchtest 指标

第一轮 rpmsg wire format 接入后，发现 mailbox/doorbell 路径仍有高频日志。普通 vring kick 本应只是通知，如果每次 kick 都走串口输出，会直接污染延迟和吞吐。因此后续将普通 doorbell 日志静默，仅保留异常和手工 mailbox reason 日志。

两轮对比：

| 指标 | mailbox 日志未完全静默 | 普通 vring kick 静默后 | 变化 |
|-|-|-|-|
| rpc_rtt avg | 34116us | 18910us | 下降约 44.6% |
| rpc_rtt p50 | 29072us | 15523us | 下降约 46.6% |
| rpc_rtt p99 | 111200us | 73379us | 下降约 34.0% |
| forward avg | 5084us | 2779us | 下降约 45.3% |
| handler avg | 53us | 8us | 下降约 84.9% |
| return avg | 24978us | 16614us | 下降约 33.5% |
| ping-pong 吞吐 | 32 msg/s | 45 msg/s | 提升约 40.6% |

静默后的最终轮输出摘要：

```text
rpc_rtt: min=1231us max=77345us avg=18910us p50=15523us p99=73379us
forward_latency: min=51us max=15971us avg=2779us p50=2403us p99=10309us
handler_time: min=2us max=58us avg=8us p50=9us p99=17us
return_latency: min=828us max=83136us avg=16614us p50=13359us p99=63238us
ping-pong: 1000 msgs, 64B each, 21792595us, rate=45 msg/s, bandwidth=2 KB/s
```

结论：串口日志会显著放大 rpmsg doorbell 路径成本。后续所有性能测试必须保持 `ICC_VERBOSE=0`，并确认普通 vring kick 不刷屏。

## 4. used ring/free list 改进指标

本轮改进把发送侧从：

```text
desc_id = avail_idx % SHMSG_SLOT_NUM
```

改为更接近 virtio split ring 的 descriptor ownership 模型：

```text
sender free list -> avail ring -> receiver consume -> used ring -> sender reclaim -> free list
```

核心收益不是同步单流吞吐，而是修正 descriptor 生命周期，为多条在途、异步批量收发、乱序回收和通知抑制打基础。

对比结果：

| 指标 | 改进前 | 改进后 | 变化 |
|-|-|-|-|
| rpc_rtt avg | 19448us | 21525us | 上升约 10.7%，QEMU 调度抖动明显 |
| rpc_rtt p50 | 16200us | 16928us | 上升约 4.5% |
| rpc_rtt p99 | 78979us | 68752us | 下降约 12.9% |
| forward avg | 3790us | 3171us | 下降约 16.3% |
| handler avg | 10us | 13us | 小幅上升，来自 reclaim/free-list bookkeeping |
| return avg | 16601us | 15909us | 下降约 4.2% |
| return p99 | 67579us | 56566us | 下降约 16.3% |
| ping-pong throughput | 50 msg/s | 48 msg/s | 同步单流基本持平 |

解读：

- 同步单流每次只有一条在途，free list/reclaim 的结构性优势不容易转化为吞吐提升。
- p99 和 return p99 有改善，说明 descriptor ownership 修正后长尾有所收敛。
- 这一步主要是 rpmsg transport 语义改进，不应只按同步 ping-pong 吞吐评价。

## 5. 零拷贝靠近、批量发送与 endpoint/ns 指标

后续在 used ring/free list 基础上继续做三类改进：

| 改动 | 说明 |
|-|-|
| RX buffer 引用入队 | ISR 不再整包复制并立即归还 used ring，而是把 `desc_id/wire_len/buf/msg` 放入 endpoint 队列 |
| xv6 TX loan/commit | 发送侧先 loan outbound buffer，原地填写 rpmsg header，再 commit 到 avail ring |
| `iccsendbatch()` | 一次发布多个 descriptor，最后只触发一次 mailbox kick |
| `vIccNsTask` | `QUARDAMP_DEMO=0` 时仍主动发布 `rpmsg-echo`、`quardamp-rpc`、`quardamp-bench` endpoint |

最终 benchtest 指标：

| 项目 | 结果 |
|-|-|
| Test 1 RPC RTT | min=3855us, max=112241us, avg=20854us, p50=16605us, p99=60843us |
| Test 2 forward | avg=3303us, p99=8618us |
| Test 2 handler | avg=16us, p99=62us |
| Test 2 return | avg=16767us, p99=70654us |
| Test 3 sync ping-pong | 1000 msgs, 22237055us, 44 msg/s, 2 KB/s |
| Test 4 batch window | 512 msgs, window=8, 2958965us, 173 msg/s, 10 KB/s |

最关键的优化指标是 Test 4：

```text
同步 ping-pong: 44 msg/s
批量 window=8: 173 msg/s
吞吐提升约 3.9x
```

这说明批量 avail 发布和通知合并已经生效。同步 RPC 路径仍主要受 xv6 调度、timer 粒度和串行 request/reply 模型影响，所以 RTT 均值没有随批量路径同步下降。

## 6. Buddy 页面分配器指标

当前 xv6 的 Buddy 分配器替换原版单页 freelist，但保持 `kalloc()` / `kfree()` 作为 order-0 包装，原有调用者无需改动。

关键指标：

| 指标 | 当前值 | 含义 |
|-|-|-|
| 管理范围 | `KERNBASE=0x82000000` 到 `PHYSTOP=KERNBASE+128MB` | 适配 OpenSBI S-mode xv6 的内存布局 |
| 最大 order | 11 | 最大连续块为 `2^11` 页 |
| 最大连续分配 | 8MB | `2048 * 4KB` |
| 最小分配 | 4KB | order 0，兼容原 xv6 `kalloc()` |
| 页元数据 | 约 32B/page | `struct page` 保存 prev/next/order/allocated |
| 元数据总开销 | 约 1MB | 128MB / 4KB = 32768 页，32768 * 32B = 1MB |
| 元数据占比 | <1% | 相比 128MB 总内存可接受 |
| 分配复杂度 | O(MAX_ORDER) | 从目标 order 向高阶找空闲块，最多 12 阶 |
| 释放复杂度 | O(MAX_ORDER) | 通过 `pfn XOR (1 << order)` 逐级尝试合并 |
| 空闲块摘除 | O(1) | 每阶使用双向链表，合并时可直接摘除 buddy 块 |

Buddy 的主要性能价值是提供物理连续页能力，而不是让 order-0 单页分配更快。相比原 xv6 freelist，它增加了少量元数据和 split/merge 成本，但换来后续 DMA buffer、大页映射、共享内存窗口等连续物理内存需求。

## 7. Slab/SLUB 风格小对象指标

当前实现更准确地说是 xv6 上的 Slab 分配器，具备部分 SLUB 风格目标：小对象复用、按 size class 管理、释放后可回收到 Buddy。文档里提到的 `slub` 指标可按本项目 `slab` 实现来对应。

Size class：

| 对象大小 | 每页 slot 数 | 典型用途 |
|-|-|-|
| 32B | 约 124 | 小结构体 |
| 64B | 约 62 | `struct file` 等 |
| 128B | 约 31 | inode 类对象 |
| 256B | 约 15 | 中型缓冲 |
| 512B | 约 7 | 小对象缓存 |
| 1024B | 3 | `struct pipe` |
| 2048B | 1 | 接近半页的大对象 |

`pipe.c` 已经从整页 `kalloc()` 改为：

```text
kmalloc(sizeof(struct pipe)) / kfree_obj()
```

`struct pipe` 约 540B，落入 1024B class。原方案每个 pipe 独占 4096B，改后每页可容纳 3 个 pipe。

最终 `slabtest` 实测：

```text
[1024 B] per_slab=3 allocs=30 frees=30 active=0 pages=1 reclaim=5

without slab: 30 pages
with slab: 10 pages
pages saved: 20 (66 percent reduction)
pages reclaimed: 5
active objs: 0
```

指标解读：

| 指标 | 实测值 | 含义 |
|-|-|-|
| allocs/frees | 30/30 | 5 轮 x 6 pipe，全部正确释放 |
| active | 0 | 无对象泄漏 |
| pages | 1 | 释放后保留 1 个热缓存 slab 页，避免频繁抖动 |
| reclaim | 5 | 每轮多余全空 slab 页归还 Buddy |
| pages saved | 20 pages | 相比整页分配节省 2/3 页面 |
| reduction | 66% | 核心内存节省指标 |
| 利用率变化 | 约 13% -> 约 75% | 540B/4096B 到 3*1024B/4096B |

这组数据证明三件事：

- Slab/SLUB 风格小对象缓存显著降低 pipe 对象的页内碎片。
- `reclaim=5` 说明全空 slab 页确实归还给 Buddy，不是只申请不释放。
- `active=0` 说明 kmalloc/kfree_obj 接入 pipe 后没有引入泄漏。

## 8. 后续优化方向

通信路径：

- 在当前 descriptor ownership 模型上做多 in-flight RPC bench，不只测同步 ping-pong。
- 增加 event_idx / no_notify 类中断抑制，减少高吞吐阶段 doorbell 次数。
- 补齐更完整的 endpoint 动态创建、销毁和 ns 发现流程。
- 若要做用户态 true zero-copy，需要设计 buffer handle、release syscall、权限隔离和异常退出回收。

内存路径：

- 给 Buddy 增加统计 syscall，例如各 order 空闲块数量、最大可分配连续块、split/merge 次数。
- 将更多内核对象逐步迁移到 Slab，例如 `struct file`、inode 缓存等。
- 做 per-CPU slab cache，减少多核下全局 size class 锁竞争。
- 增加 slab double-free 检测或 freelist poisoning，提升调试能力。
